# ADR-12: Observability

## Context
The Modular Monolith needs operability and diagnosis distinct from financial auditability, covering failure detection, technical investigation, performance, and recovery understanding, without premature distributed tracing or vendor lock-in.

## Decision
Establish minimum observability for the Modular Monolith and explicitly distinguish Observability from Auditability. Observability serves operating, diagnosing, detecting failures, investigating technical issues, assessing performance, and understanding recovery. Auditability serves reconstructing financial facts and proving who did what with traceability.

MVP conceptual minimum: structured logs with enough correlation to diagnose operations without unnecessary sensitive data; conceptual metrics covering at least operation rate, latency, errors, failures, saturation, and relevant financial-operation behavior; correlation across monolith layers using conceptual operation id, correlation id, and request/interaction id when applicable. Credentials, tokens, sensitive personal data, balances, and other sensitive financial information MUST NOT be logged unnecessarily. Future evolution toward distributed tracing, APM, dashboards, alerting, SLOs, and distributed observability for separated services remains OPEN.

## Consequences
- What becomes easier: diagnosable monolith; correlated operations; failure and recovery insight.
- What becomes harder: tooling, sampling, dashboards, and SLOs still required later; sensitive-data discipline required.
- Trade-offs: minimal correlation now versus full distributed observability later only if services separate.

No vendor, agent, specific tool, mandatory OpenTelemetry, concrete APM, dashboard, concrete sampling, Kubernetes, or distributed infrastructure selected here.

## Alternatives Considered
- Minimal structured logs plus base metrics plus correlation -> Selected for MVP.
- Full distributed tracing/APM now -> Deferred: unnecessary without separate services.
- Logs only without correlation -> Rejected: insufficient diagnosis.
- Vendor-locked observability now -> Rejected: premature commitment.

## Status

Accepted - formally approved by human review (2026-10-18), with the minimum binding scope
recorded in "Acceptance Supplement" below. Everything outside that scope remains OPEN exactly
as decided originally.

Acceptance record: this acceptance covers the architectural direction and the minimum binding
scope only. It is not evidence that any observability component exists; implementation requires
a separate, explicitly scoped approval and is not authorized by this ADR.

## Acceptance Supplement (2026-10-18)

This supplement adds binding scope to the decision above. It does not repeal it: where this
supplement is silent, the original decision stands unchanged.

### Minimum scope made binding (MUST)
Structured diagnostic logs with correlation, plus base technical metrics. Nothing beyond this
becomes mandatory by this acceptance.

### Identifier contract
- `correlationId` links records belonging to the same interaction. It is accepted from the
  incoming request only when it passes strict validation; otherwise a new value is generated.
  This ADR establishes the bound `^[A-Za-z0-9._-]{1,64}$` as a NEW convention for this
  identifier, chosen to mirror the character set and maximum length already applied to the
  client-provided `customerId`; it does NOT establish a general rule for every external
  identifier of the system. A malformed or hostile value MUST NOT fail, alter, or block the
  request: it is replaced. It is never an authorization or identity input.
- `requestId` identifies one HTTP request and is always generated by the application; it is
  never accepted from the client.
- `operationId` identifies a business operation and exists only where the owning contract
  already provides it. It MAY be propagated to diagnostics only where it already exists and its
  use is permitted. The HTTP layer MUST NOT invent a financial operation or assert that a
  request corresponds to a confirmed one.
- The `correlationId` is the ONLY identifier echoed in the response, so a client can quote it;
  `requestId` stays internal to diagnostics. Both are removed from the diagnostic context in a
  `finally` block, so a pooled thread cannot carry them into a later, unrelated request.

### Diagnostic HTTP logging (bounded, not indiscriminate)
- One structured record per request that reaches an instrumented component, carrying
  `correlationId`, `requestId`, HTTP method, route template (never the raw URI or query string),
  status, duration, and `operationId` where already available and permitted. No duplicated
  records for the same request.
- Recording depends on control reaching an instrumented component. A request that never reaches
  the application cannot be recorded by any filter, and this acceptance does not claim
  otherwise; whenever the request does reach the instrumented boundary, the record MUST exist
  without dumping request data.
- Exceptions are recorded by type and correlation reference, without bodies, payloads, or
  sensitive values.

### Data that MUST NOT be logged
Credentials, tokens, request and response bodies, `Idempotency-Key`, `Idempotency-Key-Hash`,
`X-Actor-Id`, any account, customer or beneficiary identifier, balances, amounts, and personal
data. The allow-list above is exhaustive for this increment: what is not listed is not logged.
The audit trail retains the already authorized details per ADR-11; diagnostic logs MUST NOT
mirror them.

### Technical metrics only
Base technical metrics compatible with the existing stack: HTTP server metrics and JVM metrics
through the framework's default instrumentation. Metrics MAY be collected and held internally;
collection does NOT require HTTP exposure. Datasource-pool metrics are NOT a requirement: they
depend on the configured pool and its available instrumentation and MUST NOT force a specific
data-access technology. No business or financial metric is required by this acceptance; any
future business metric MUST be designed so that it exposes no account, customer or financial
data. No additional storage, export or registry technology is selected here.

### Management endpoints
Over HTTP only the health endpoint MAY be exposed. Metrics and any diagnostic endpoint MUST NOT
be exposed over HTTP without a separate, explicit security decision; every other management
endpoint stays disabled. The existing configuration already lists `info` in the exposure list:
that entry MUST NOT become effective until the fields it would expose are explicitly approved.
"Static build information", if ever approved, means at most the pre-existing build metadata
(project name, version, build time); it is NOT enabled by this acceptance. Exposure MUST be
configured deliberately and MUST NOT appear as a side effect of adding a dependency.

### Tooling concretized here
SLF4J with the framework's default logging backend, plus the framework's actuator and metric
facade. No APM, no OpenTelemetry, no external registry or vendor exporter. This is where the
tooling left open by ADR-01 ("logging framework") and by ADR-11 ("logging tool") is concretized
for logging and metrics. ADR-01, ADR-11 and ADR-17 are NOT amended by this acceptance, and
everything they leave open outside this supplement (retention, sampling, dashboards, alerting,
SLOs, distributed tracing) remains OPEN.

### Placement (with the existing modular rules, and no new rule)
The HTTP correlation filter and its configuration MUST live in the application wiring package.
That package MUST NOT become a module of transversal logic, MUST NOT create a `shared` package,
and MUST NOT introduce dependencies across module boundaries: it MUST NOT reach any module's
`internal` package, and no business module MAY depend on it. This matches the current state (no
production class outside the wiring package references it) and the documented convention of
that package; it relies on the rules that already exist and are green. This acceptance
introduces NO new ArchUnit rule, and MUST NOT require changing the existing ones. If the
concern grows beyond HTTP correlation, promoting it to a transverse capability with its own
owner requires its own separate justification.

### Separation from auditability
Diagnostic logs serve technical diagnosis, do not replace and MUST NOT duplicate the audit
trail, MUST NOT write audit events, and MUST NOT access any audit internal package. The shared
correlation identifier is the only bridge between the two.

### Identity is not addressed here
Nothing in this supplement reduces the `X-Actor-Id` spoofing risk. Authentication and
authorization remain a separate, open security decision that this acceptance does not
pre-empt.

### Out of scope (remain OPEN)
Distributed tracing, APM, dashboards, alerting, SLOs, sampling, retention, business metrics,
and any business/operation logging inside the financial modules.

### Verification obligations (implementation phase, separately authorized)
Correlation propagation across layers; diagnostic-context cleanup with no leakage across pooled
threads; rejection or replacement of malicious and malformed incoming correlation identifiers;
absence of sensitive data in logs; the set of exposed management endpoints; and the existing
ArchUnit rules remain green and unchanged.

## Implementation status and audit record (2026-10-18)

This record registers what was implemented and verified, and nothing more. It does not widen the
binding scope above, and it keeps three different states apart: architectural acceptance (this ADR),
verified implementation (below, according to the cited evidence), and integration into the main
branch, which has NOT happened: the work is committed on `docs/account-movement-history-closure`
(`eb22acc`, `53988ec`, `9bbc7bb`), published in PR #14, and is not part of `main`. It also
clarifies, without rewriting it, that the "Acceptance record" statement above
("it is not evidence that any observability component exists") describes the acceptance date:
implementation was authorized afterwards, phase by phase, and is reported here.

Implemented in the application wiring package (`com.bancoelcapital.app`), as the only production
change of this increment:
- `CorrelationIds` (identifier contract), `CorrelationIdFilter` (diagnostic HTTP correlation) and
  `ObservabilityConfig` (single `FilterRegistrationBean` registration, no stereotype annotation on
  the filter).
- `spring-boot-starter-actuator` as the only added dependency, together with
  `management.endpoints.web.exposure.include: health` and
  `management.endpoint.health.show-details: never`, changed atomically with that dependency so the
  pre-existing `info` entry never became effective.
- Apart from the documentation of this ADR, no production, configuration, migration or workflow file
  was modified.

Evidence cited (30 new tests in that package; 449 tests run, 0 failures, 0 errors, 0 skipped, with
Spotless and Checkstyle clean; the run excludes the PostgreSQL-tagged tests, which need Docker):
- `CorrelationIdsTest` (8) and `CorrelationIdFilterTest` (8): identifier bound, replacement of
  malformed and hostile values, HTTP echo, diagnostic-context cleanup including a failing record, and
  the logging allow-list with sentinel values.
- `ObservabilityConfigTest` (3), `ActuatorExposureTest` (5) and
  `ActuatorExposureUnderTestProfileTest` (6): real HTTP (`@SpringBootTest(webEnvironment =
  RANDOM_PORT)`) for single registration, order, HTTP correlation on management routes, and the
  exposed management endpoint set, the last class under the `test` profile.
- `ModuleBoundariesTest` (65) and `SmokeTest` (1) remain green with no ArchUnit rule added or
  changed.

Interpretations accepted by review, recorded as interpretations and not as implicit approvals:
- The `operationId` field of the diagnostic record is NOT emitted. The conditional "where already
  available and permitted" is not met at the HTTP boundary: the identifier is created inside the
  financial services and the HTTP layer MUST NOT invent an operation or assert that a request
  corresponds to a confirmed one, so propagating it would be a separate design decision.
- Correlation propagation across layers is satisfied as a mechanism only: the identifiers live in
  the diagnostic context for the whole request thread and the `correlationId` is echoed to the
  client, but no component outside the filter consumes them yet, because logging inside the financial
  modules remains out of scope.

Declared implementation limits (documented, not new scope):
- Only the initial `REQUEST` dispatch is recorded: `ERROR`, `ASYNC`, `FORWARD` and `INCLUDE`
  dispatches are skipped deliberately, so asynchronous request processing is not covered.
- When an exception escapes the filter, the recorded status is the value observed at that point; the
  final status is decided by the container afterwards, and this record does not claim to capture it.
- Errors (as opposed to exceptions) are not classified by type; they propagate with
  `exceptionType=none`.
- The route template is whatever Spring MVC actually selected: `unmatched` when no handler matched,
  and the matched pattern otherwise. A 404 served by the static resource handler therefore reports
  the resource pattern, which is truthful for diagnosis and is not the requested path.
- The filter order (`Ordered.HIGHEST_PRECEDENCE`) is an implementation decision of this increment,
  pinned by a test, and not a literal requirement of this ADR.
- No further instrumentation was added. A read-only runtime probe of the framework's default
  instrumentation observed 62 technical meters (HTTP server and JVM, plus the pre-existing
  datasource pool) collected internally, with no HTTP exposure of metrics.

Evidence limitation that MUST NOT be read away: the local HTTP evidence was produced over H2. The
increment has NOT been validated against PostgreSQL locally. It WAS validated against PostgreSQL in
CI on `9bbc7bb`: 80 PostgreSQL tests ran with 0 failures, 0 errors and 0 skipped, and the anti-skip
gate passed. That CI run is evidence for the PostgreSQL test suite; it is not a local observation
and does not by itself extend the H2-based health and exposure evidence above to PostgreSQL.

Pending, unchanged by this record: the interpretations above stand until a separate decision
resolves them; identity (the `X-Actor-Id` spoofing risk) remains an open, separate security decision;
and integration into the main branch, together with any derived correction, requires separate
authorization.
